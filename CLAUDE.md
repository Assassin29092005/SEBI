Facts, review state, and user accounts live in Postgres (see `backend/app/db.py`, `backend/app/db_models.py`); the checked-in `docker-compose.yml` runs a single dev-grade Postgres instance, and each test in the suite runs inside one DB transaction (`conftest.py`'s `db_session` fixture) that's rolled back at the end, so tests never need a full DB reset between runs. `DATABASE_URL`/`TEST_DATABASE_URL` env vars override the defaults, which match `docker-compose.yml` exactly.

Tests default to the deterministic (non-LLM) path — an autouse `conftest.py` fixture blanks the API keys so the suite never depends on live Gemini/Groq quota. Opt a specific test into real network calls with `@pytest.mark.live_llm`.

`.env` is optional. The demo and every user-facing feature run key-free — every LLM path (`extract_facts`, `generate_section`, `examine`, contradiction refinement) catches `LLMUnavailable` from `app.llm.client.grounded_complete` and continues on a deterministic implementation. See README.md § "The whole system runs without any API key" for the per-feature fallback table.

## Project Overview

**SME IPO Offer Document Drafter** — an AI-assisted drafting platform built for the SEBI hackathon (Problem Statement 4: Simplifying IPO Offer Document Preparation for SMEs). Working name: **DRHP Studio**.

### The Problem

SME listings on the SME Exchange platforms (BSE SME, NSE Emerge) are throttled by the cost and months of effort needed to prepare a compliant IPO offer document. Promoters with lean teams and no capital-markets exposure depend on merchant bankers, lawyers, and compliance professionals from day one. SEBI explicitly wants the early drafting stage simplified — while **preserving the role of authorised intermediaries in review and certification before any regulatory submission**.

### What We're Building

A pipeline where an SME promoter enters their business, financial, and legal particulars (or uploads documents they already have) and receives a substantially complete, disclosure-ready **draft DRHP** under SEBI ICDR Chapter IX, with gaps and inconsistencies flagged and the merchant banker kept in the certification loop. "TurboTax for IPO paperwork."

The full version, in pipeline order:

1. **Eligibility gate** — fail fast against Chapter IX / exchange eligibility norms. A failed gate produces a **readiness report** (what to fix, indicative timeline), not a dead end — this is how the tool *broadens the pipeline* of SMEs rather than only serving the already-ready.
2. **Three intake channels** — a multilingual guided wizard (plain language; every question shows *why it is asked*, with the regulation clause it maps to), document uploads with auto-extraction (native text layer, or OCR via a real Tesseract install for scanned/photographed pages — real SME paperwork rarely arrives as clean digital text), and a litigation lookup (real API — api.indiankanoon.org, published judgments — with an offline mock fallback; see Limitations for what it can't tell you).
3. **Promoter confirmation of every extracted fact** — auto-extracted values are *proposals* until the promoter confirms them against the highlighted source snippet. Extraction accuracy is a first-class check, distinct from cross-document consistency. An unconfirmed fact never feeds generation.
4. **Fact store with provenance** — one structured store; each fact carries its source (wizard answer / document + page / lookup), extraction confidence, confirmation status, and the **role** that supplied it (promoter / auditor / merchant banker / system).
5. **Machine-readable checklist schema** — SEBI ICDR Chapter IX plus the current amendments, encoded as versioned data (see "The Checklist Schema" below). The schema is the single source of truth: no disclosure requirement lives in prompts or code. It is regenerable from the regulation text when SEBI amends rules.
6. **Grounded generation** — the LLM writes each section using *only* facts from the store. Anything missing renders as `[REQUIRES INPUT: <fact> — <who can provide it>]`. Honest blanks beat confident hallucination; this is the core trust guarantee.
7. **Validation suite** — gap check (schema vs. fact store), contradiction check (numeric/entity consistency across sections — "page 40 disagrees with page 12"), boilerplate detector, and an **adversarial examiner agent** that plays exchange reviewer and raises objections until the draft survives them.
8. **Role-aware gap report** — every gap is routed: *promoter-fixable*, *needs your auditor* (e.g. restated financial statements, which the tool can ingest and format but never generate), or *needs your merchant banker* (e.g. due-diligence certificate). This routing is what makes "substantially complete" an honest, defensible claim.
9. **Banker certification workflow** — a dashboard with per-section review states (`draft → reviewed → certified`), an audit trail of banker edits, and a **certification lock**: the exchange-ready package cannot be exported until every blocker-severity section is certified. This is a feature demanded by the problem statement, not an apology.
10. **Document assembly** — python-docx produces the formatted draft DRHP **and the DRHP-stage draft abridged prospectus**. ✅ RESOLVED (2026-07-03): the ICDR (Amendment) Regulations, 2026 (effective 2026-03-21) omit the "Offer Document Summary" (old Sch. VI Part A para 4) and mandate a **draft abridged prospectus per Schedule VI Part E** filed with the draft offer document (Reg. 246(3)). See `data/regulation/MANIFEST.md`.
11. **Quantitative coverage score** — completeness measured per-section against real filed SME DRHPs, with auditor-only content explicitly marked out-of-scope rather than silently counted. Judges get evidence, not a claim.

## Guiding Principles

- **Schema first.** The checklist schema is the single source of truth and the first thing built; everything downstream inherits its quality. If the schema is wrong, the generator, validator, gap report, and coverage score are all wrong together.
- **The LLM never invents a fact.** Generation is grounded in the fact store only. Missing data → `[REQUIRES INPUT]`. No exceptions, ever — one hallucinated number on stage destroys the entire trust pitch.
- **Every sentence is traceable.** Facts carry provenance from intake; every generated sentence carries a clickable citation back to its evidence. This is the differentiator over "anyone can make an LLM write a document."
- **Intermediaries stay in the loop by design.** The problem statement *requires* preserving the merchant banker's review/certification role. The certification lock is a selling point — never frame the tool as replacing intermediaries, only as compressing the early drafting stage.
- **Role-based truth.** Some content can only lawfully enter via the auditor or banker role (restated financials, due-diligence certificate). The tool ingests and formats such content; it never generates it. Define "substantially complete" as coverage of the narrative/disclosure sections — say so openly. Correction rights are not symmetric with confirmation rights: any role may only *confirm* a fact it supplied (vouching for your own submission), but a banker may *correct* any fact regardless of supplier — due-diligence review means catching someone else's error, and `app.extraction_reliability` exists to measure exactly that.
- **Promoter-first UX.** "Simple enough for a first-time issuer" is a graded criterion, not a nice-to-have. Plain language, vernacular support, clause-linked "why we ask this" explanations, visible progress. The demo opens with the promoter journey, not the pipeline.
- **Regulatory currency.** Pin the exact regulation version (ICDR as amended through March 2026) in the schema header. Cite the clause for every requirement. When SEBI amends, regenerate the schema — don't patch code.
- **Demo-ready over production-ready.** Hackathon rules: a compelling end-to-end demo (eligibility → intake → confirm → generate → validate → banker certify → export) with one clearly synthetic demo company. Note production concerns in comments/docs rather than building them.

Repo layout (built):

- `backend/app/db.py` / `backend/app/db_models.py` — async Postgres engine/session (`get_session()` FastAPI dependency) and SQLModel table definitions (`users`, `facts`, `section_states`, `banker_edits`, `audit_events`). `backend/app/facts_repo.py` and `backend/app/review/repo.py` are the async repository functions translating those tables to/from the pure, DB-free `Fact`/`ReviewState` Pydantic models everything else uses — `generate/`, `validate/`, `coverage.py`, and `assemble/` never talk to Postgres directly. `backend/migrations/` (Alembic, async) holds the schema migrations; `docker-compose.yml` at the repo root runs Postgres for local dev (`docker compose up -d`, then `alembic upgrade head` from `backend/`).
- `backend/app/audit.py` — audit log: who accessed or changed what, and when. Wired as a single ASGI middleware in `main.py` (`audit_log_middleware`) rather than scattered per-endpoint calls, so it covers every request automatically — views, confirmations, corrections, generation, exports, document downloads, logins, and access denials (401/403) alike. `classify_request` turns method+path into a human-readable action/resource label; storage is the append-only `audit_events` Postgres table (`AuditEventRow` in `db_models.py`), indexed on exactly the columns `GET /api/audit` (banker-only, the review surface) filters and orders by. It was a flat encrypted file until the audit-completion pass — a read-modify-write of the whole log on every request, i.e. O(n) per request on a log that only grows, which is precisely what an append-only table exists to solve. The middleware opens its own short-lived session for the write rather than reusing the request's (that one is already closed by the time the response is in hand), and `record_audit_event` swallows every exception: audit logging must never be able to break the request it is observing. Extends the two audit mechanisms that already existed — fact provenance (who *supplied* a value) and the banker review audit trail (who *edited* a section) — to the "who *looked at* this" half of the picture.
- `backend/app/crypto.py` — encryption at rest (Fernet/AES-128-CBC+HMAC), keyed by `Settings.encryption_key`, for the one thing still on the filesystem after facts/review/users/audit moved to Postgres: archived original uploads (see below). Same ephemeral-key-with-a-warning fallback pattern as the JWT secret.
- `backend/app/rate_limit.py` — in-memory sliding-window rate limiter, wired as the innermost `@app.middleware("http")` in `main.py` so a 429 is still audited and still counted in metrics. No Redis, no `slowapi` — a dict of per-key timestamp windows behind a `Lock`, matching the zero-extra-infrastructure posture of the rest of the app. Auth endpoints (`/api/auth/login|register`) are keyed by client IP, since brute force is exactly the case where no token exists yet; everything else is keyed by the token's `sub` claim, so a user cannot double their budget by logging in twice. Limits are per-route (LLM-touching generation 5/min, the SEBI regulatory-watch scrape 3/min, uploads 20/min, everything else 60/min). Drained keys are deleted rather than left as empty lists, so the key dict cannot grow without bound. `Settings.rate_limit_enabled` turns it off — the test suite does exactly that (`conftest.py`), because the windows are wall-clock and the suite fires hundreds of requests per second.
- `backend/app/metrics.py` — in-process request metrics (per-route counts, error counts, mean and p95 latency, status-code histogram), recorded from the audit middleware since that is already the outermost timing point. Keyed by *route* (`GET /api/facts/{id}/confirm`), never by raw path, or one counter per fact id would leak; latency samples are a bounded `deque` while counts stay exact, so memory is O(routes) not O(requests served). `GET /api/metrics` (banker-only, same oversight rationale as the audit log). A real deployment would swap this for Prometheus + Grafana; this is what makes the app observable without adding infrastructure to run.
- `backend/app/schema/clause_text.py` — clause-text retrieval: resolves a checklist entry's `clause_ref` citation string to the actual ICDR passage in `data/regulation/`, so a promoter can read the regulation instead of taking the citation on trust. Fails **closed**: an unresolvable ref returns `None` and the UI shows nothing, because a *wrong* passage displayed next to a citation would undermine the exact traceability guarantee the feature exists to strengthen. Schedule VI Part A's eighteen top-level paragraph titles are pinned as hand-verified data (`_PART_A_TITLES`) rather than inferred — Part A's nested lists reuse the same `(N)` numbering as its top-level paragraphs (para (5) Risk factors alone contains its own (1)–(31)) and the PDF text layer carries no indentation, so every purely structural heuristic tried here mis-segmented at least one real paragraph. The regulation version is pinned anyway and the schema is human-reviewed legal-adjacent content by policy, so pinning the titles is consistent with both. `GET /api/schema/clause/{clause_ref:path}` and `GET /api/schema/clauses`; `frontend/src/components/ClauseTextViewer.tsx` is the shared expand-on-click chip, used in the Gap Report's per-gap detail panel and beside clause-carrying findings in `DraftViewer.tsx`.
- `backend/app/intake/vault.py` — encrypted archive of original uploaded documents (`archive_upload` / `retrieve_upload` / `list_archived_uploads`). Extraction used to only ever hold the bytes in memory for one request, so nothing let a banker check a fact's snippet against the actual source document — this closes that gap. One `<uuid>.enc` file per upload; `GET /api/uploads` / `GET /api/uploads/{id}` in `main.py` expose it to any authenticated user, same read access as the fact store.
  - **Inline document viewer** (polish on the fact-confirmation trust mechanic, CLAUDE.md's "confirm... against the highlighted source snippet"): `app.intake.uploads.uploads_extract` now captures `archive_upload`'s returned `document_id` and threads it onto every `ExtractionProposal` it produces, and `proposal_to_fact` carries it (plus `page`/`source_file`) onto `Fact.provenance` — three new additive, optional fields (`Provenance.document_id`/`page`/`source_file` in `app.facts`; `provenance_document_id`/`provenance_page`/`provenance_source_file` columns on `FactRow`) so both a still-pending proposal and an already-confirmed fact can link straight back to their real source document, not just a quoted snippet string. `GET /api/uploads/{document_id}/page/{page_number}` (any authenticated user) renders one PDF page as a PNG via `app.intake.ocr.render_pdf_page_with_highlight`, which uses PyMuPDF's `search_for`/`add_highlight_annot` to actually highlight the snippet where the page's own embedded text layer contains it — real, pixel-drawn highlighting, not a client-side approximation. That only works when the PDF has a native text layer: an OCR'd/scanned page has none for `search_for` to match against, so the page still renders but without the highlight overlay — an honest, documented limitation (pixel-precise OCR highlighting would need Tesseract's own per-word bounding boxes, a materially bigger capability this doesn't attempt), not a bug. `frontend/src/components/DocumentSnippetViewer.tsx` is the shared, lazily-loaded viewer (collapsed by default) used by both `Wizard.tsx`'s `ProposalCard` (the primary fact-confirmation moment) and `DraftViewer.tsx`'s `FactPanel` (citation review): PDFs render via that page-image endpoint, standalone image uploads display directly, and `.txt` uploads are fetched as raw text and highlighted client-side by an exact substring match — the one case where the highlight is character-perfect, since there's no rendering step to lose position across. Fetching an authenticated image needed a new primitive (`apiGetBlobUrl` in `api/client.ts`): every endpoint requires a Bearer header, which a plain `<img src>`/`<a href>` cannot attach, so the helper fetches with `fetch()` + the same auth header every other request uses and hands back a `URL.createObjectURL` blob URL instead — the same fix the pre-existing `assembleUrl`/`bundleUrl` download links in `DraftViewer.tsx`/`BankerDashboard.tsx` still need (found while building this: those are plain `<a href>`s pointed at auth-required endpoints and 401 on a real click today — a pre-existing bug, not introduced or fixed here).
- `backend/app/auth/` — real authentication + server-side RBAC: `models.py` (User/UserPublic, register/login shapes), `security.py` (PBKDF2 password hashing, JWT issue/verify), `store.py` (Postgres-backed, async repo functions), `dependencies.py` (`get_current_user` / `require_roles(...)` FastAPI dependencies), `router.py` (`/api/auth/register|login|me`). Promoter self-registers; auditor/banker require an invite code (`Settings.auditor_invite_code` / `banker_invite_code`) — those roles carry certification and role-tagged-upload authority. Every endpoint in `main.py` depends on one of these; the old frontend role dropdown was UI-only and is gone.
- `backend/app/schema/` — checklist YAML + Pydantic loader/validator + `applicability.py` (evaluates conditional `has_<fact>` requirements against the fact store; unrecognised conditions default to applicable — over-disclosing is safe, silently dropping a requirement isn't).
- `backend/app/eligibility.py` — eligibility gate rules + readiness-report generator.
- `backend/app/intake/` — wizard question flow + `question_copy.yaml` (schema-derived, multilingual), upload handling/extraction (LLM + deterministic label-scan fallback, both reading from `ocr.py`-produced per-page text — native PDF text layer where one exists, real Tesseract OCR otherwise; OCR-sourced facts carry a lower confidence, see `_OCR_CONFIDENCE`), litigation connector (`IndianKanoonConnector` — real HTTP integration against api.indiankanoon.org, request shape verified against the API's own reference client — wrapped by `FallbackLitigationConnector`, which falls back to the offline `MockLitigationConnector` when no provider is configured or the call fails; same optional-real-integration pattern as `app.llm.client`).
- `backend/app/facts.py` — fact store: immutable facts with provenance, confidence, confirmation status, supplying role.
- `backend/app/llm/client.py` — the single provider-agnostic LLM client (Gemini / Groq); raises `LLMUnavailable` when no key is configured or the call fails, which is what every LLM-dependent feature falls back to a deterministic path on.
- `backend/app/generate/` — per-section generation: schema requirement → retrieval of relevant facts → grounded prompt → section text with citations and `[REQUIRES INPUT]` markers. Recomputes `*_paise` values deterministically from the matched snippet rather than trusting LLM arithmetic.
  - `translate.py` — vernacular draft generation: extends the wizard's EN/HI intake toggle (`app.intake.wizard.SUPPORTED_LANGUAGES`, reused directly rather than a second language list) to the *drafted* text itself, for promoter review only — the filed DRHP is never translated or re-assembled, only the on-screen section text. This is the one LLM-touching feature in the whole app with **no deterministic fallback** (translation has no non-LLM implementation): `GET /api/sections/{entry_id}/translate?lang=hi` always answers `200` with a `TranslatedSection {entry_id, lang, text, translated}` — `translated: false` is the honest "didn't translate this time" signal (no key configured, the call failed, or the guard below rejected it), with `text` degrading to the untouched English original rather than a blank page or an error. Guard: every digit sequence in the translated text must appear verbatim in the already-approved English original (`_preserves_numbers` — a plain substring check, no fact-store lookup needed, since that English text was already ground-guarded once by `generate_section`'s own hallucination guard when it was first written); a translation that fails this is discarded exactly like `generate_section` discards LLM output that fails its own guard. Deliberately does **not** try to preserve citation spans across translation (character offsets can't survive an LLM rewrite) — `DraftViewer.tsx`'s Hindi view shows plain translated prose with a note that citations stay on the English original, not an attempt at aligned bilingual citations.
- `backend/app/validate/` — gap checker, contradiction detector (extract all numeric/entity claims, cross-check), boilerplate detector, adversarial examiner agent, and `arithmetic.py` (Objects-of-Issue arithmetic: objects sum + GCP ≟ issue size, GCP cap per Reg. 230(2); handles a contradicted issue size without crashing).
  - Four deterministic compliance validators added in the audit-completion pass, all reading *confirmed facts only* (an unconfirmed proposal isn't part of the draft, so objecting to it would flag data the promoter hasn't vouched for) and all exposed as `GET /api/validate/<kind>` to any authenticated user: `identifiers.py` (PAN/CIN/GSTIN **format** checks — catches typos, truncation, and OCR misreads that break the structure; explicitly does *not* verify the identifier is registered with any authority), `rpt.py` (every entity named in a related-party disclosure should also appear in the promoter-group list; disclosed RPT amounts should carry a materiality policy; an issuer with no RPT data at all is prompted for an explicit nil declaration), `lock_in.py` (minimum promoter contribution ≥ 20% of post-issue capital per Reg. 236(1), and stated lock-in periods against the Reg. 238–241 minimums — integer paise throughout, never floats), and `pricing.py` (issue price ≥ face value, price-band spread, PE computed from EPS cross-checked against the stated PE, premium over industry PE — `Decimal` for the ratios). `frontend/src/pages/DraftViewer.tsx`'s "Compliance checks" panel runs all four in one `Promise.all` and renders them as one list, including the checks that *pass* — an empty panel would otherwise be indistinguishable from "not run".
  - `examiner.py`'s own docstring claims the examiner "raises objections ... until the draft survives them," but `examine()` itself runs exactly once — it never re-checks whether its own objections got addressed. `iterative_examiner.py` is what makes that claim true: `examine_iteratively()` loops revise-then-re-examine until a round raises no objection unseen in an earlier round. Only *non-structural* objections (boilerplate flags, free-text LLM-reviewer prose) trigger a revision attempt — a rewrite via `app.generate.sections.generate_section`'s optional `feedback` parameter, folding the objection text into the prompt but going through the exact same hallucination guard as first-pass generation, so a revision can never be less safe. *Structural* objections (missing fact, cross-section contradiction, arithmetic mismatch, low-confidence extraction — identified by the fixed phrasing prefixes `examine()`'s deterministic pass always uses) are never revision targets: no rewrite fixes a data problem, only a new or corrected fact does. A draft whose only remaining objections are structural still converges (the loop recognises nothing more can be done and reports `stop_reason: "no_revisable_objections"`), it just doesn't `survive`. `POST /api/validate/examiner/iterative` (promoter-only, same restriction as `POST /api/generate` since it can rewrite draft text; `max_rounds` bounded `[1, 5]`) requires generation to have already run, and caches its `final_sections` back the same way `/api/generate` does — every downstream read reflects the post-revision draft. `frontend/src/pages/DraftViewer.tsx`'s "Run examiner until it survives review" button surfaces the round-by-round history and the final stop reason.
  - `suggestions.py` — auto-suggested fixes: turns validator *output* into a concrete next action, never a new invented fact or number. Three categories, each computed purely from data another validator already produced: arithmetic (the exact reconciling paise amount for `objects_overallocated`/`unallocated_proceeds`/`gcp_cap_breach`, taken straight from `ArithmeticFinding.expected_paise`/`actual_paise`), low-confidence extraction (a jump-to-source pointer — `fact_id`/`document_id`/`page` — for any confirmed, *document*-sourced citation under the examiner's own 0.7 threshold; a low-confidence *wizard*-sourced fact is deliberately exempt, since a promoter typing an answer isn't "extraction" needing re-verification), and boilerplate (one deduplicated pointer per flagged entry at the iterative examiner, which already knows how to revise that kind of objection). Deliberately does **not** cover missing-fact gaps (the gap report already routes those by role) or contradictions (no safe way to suggest which of two disagreeing confirmed values is correct without guessing one). `GET /api/suggestions` (any authenticated user); `frontend/src/pages/DraftViewer.tsx`'s "Suggested fixes" panel (top of the Validation checks accordion, plus its own metric tile) renders each suggestion, reusing `DocumentSnippetViewer` for the jump-to-source case and linking straight to the iterative-examiner panel for the boilerplate case.
- `backend/app/diffing.py` — draft version diffing: a generic, stateless, stdlib-only (`difflib`) word-level diff between any two text snapshots the caller already has — no new stored version-history table. A custom tokenizer (`\s+|\d[\d,.]*\d|\d|\w+|[^\w\s]`) keeps a number with internal commas/decimals (`"12.50"`, `"1,00,000"`) atomic as one token rather than fragmenting it at the punctuation, while still splitting punctuation from word characters so trailing punctuation on only one side (`"shares."` vs. `"shares today."`) doesn't block the matcher from finding the shared word — both properties were found to conflict with a naive tokenizer and fixed through hand-verification before being locked in as tests. `POST /api/diff` (any authenticated user) is stateless — the frontend supplies both `before`/`after` strings itself. Two call sites: `frontend/src/components/TextDiff.tsx` (shared component, falls back to plain side-by-side text on a fetch error) renders a banker edit's before/after in `BankerDashboard.tsx`'s audit trail, and a section's pre-revision vs. final text in `DraftViewer.tsx`'s iterative-examiner panel (the frontend snapshots each section's text into `preRevisionText` right before calling `POST /api/validate/examiner/iterative`, since `IterativeExaminationReport` itself only carries `final_sections` plus which `entry_id`s were revised, not what they looked like before).
- `backend/app/review/` — banker workflow: section states, edit audit trail, certification lock.
- `backend/app/assemble/` — python-docx DRHP + abridged prospectus assembly (cover callout when confirmed issue-size facts disagree; merchant-banker disclaimer baked in) + `bundle.py` (exchange-ready ZIP: both docx + gap/contradiction/coverage/examiner/arithmetic JSON + full fact-provenance ledger + review audit trail + manifest, gated by the certification lock).
- `backend/app/coverage.py` — coverage score vs. reference filed DRHPs (real benchmark against `data/reference_drhps/`, not schema-only self-reference); auditor-only content marked out-of-scope, never silently counted.
- `backend/app/extraction_reliability.py` — banker-correction feedback loop: aggregates the fact store's existing correction chains (`Fact.provenance.supersedes`) into correction rates bucketed by `(provenance.kind, confidence band)`, using the same 0.7 low-confidence threshold `app.validate.examiner` already treats as "flag for review." Isolates a `banker_caught_count` — corrections where a **banker** fixed a fact they did *not* supply, i.e. a real due-diligence catch, as distinct from a self-correction by the original supplier. Deterministic, no LLM, recomputed fresh from the fact store on every call (same small-fact-volume assumption as the audit log, but read-only so the audit log's O(n) write caveat doesn't apply). `GET /api/extraction-reliability` (banker-only, wired in `main.py`) is the review surface; `frontend/src/pages/BankerDashboard.tsx` renders it as a summary-cards-plus-table panel, fetched non-blockingly like the contradiction/arithmetic finding counts above it. This is the mechanism behind correction authority: `_require_can_correct_fact` in `main.py` lets a **banker correct any fact**, not just their own uploads (promoter/auditor correction rights and every role's confirmation rights are unchanged) — restricting a banker to only their own due-diligence-certificate uploads would make it impossible for them to catch a promoter's misextracted figure during review, which is exactly the due-diligence authority the problem statement gives them. Every correction records who performed it (`Fact.corrected_by_role`, separate from and never overwriting `supplied_by`, which still means "whose role vouches for this value") and flows through the audit log like any other request — a banker correcting someone else's fact is *more* visible after this change, not less.
- `backend/app/regulatory_watch.py` — regulatory-staleness watcher: the checklist schema pins an exact ICDR amendment date (`ChecklistHeader.amended_through`), and a demo only ever checks that pin once at build time — production doesn't get that luxury, since SEBI amendments happen continuously. `SebiIcdrWatchConnector` is a real, working scrape of SEBI's own public site (`sebi.gov.in/sebiweb/home/HomeAction.do?doListingAll=yes&search=ICDR`, verified against the live page — a real `<table id='sample_1'>` of date/category/title+link rows, most-recent first, genuinely filtered to ICDR-tagged publications spanning circulars, consultation papers, informal guidance, and enforcement notices); parsed with Python's stdlib `html.parser.HTMLParser`, not a new dependency. SEBI publishes no documented API for this — unlike IndianKanoon, there's no reference client to verify a request shape against — so a future site redesign could break the parser; that failure surfaces as `RegulatoryWatchUnavailable`, which `check_for_staleness` turns into an explicit `checked_successfully: false`, never a silently "clean" result (conflating "the check failed" with "nothing found" would be actively misleading about the schema's real regulatory currency). Like `app.generate.translate`, this **never auto-updates the schema** — every schema change is human-reviewed per CLAUDE.md's own rule; this only routes "go check this" to a human, the same philosophy as the gap report. `POST /api/regulatory-watch/check` (banker-only, a real external HTTP call so it never fires on page load) runs a fresh check and caches it in `app.runtime_cache`; `GET /api/regulatory-watch/status` just reads that cache back. `frontend/src/pages/BankerDashboard.tsx` auto-loads the cached status (safe, no network call) but only checks on an explicit banker click. `.github/workflows/regulatory-staleness.yml` runs `backend/scripts/check_regulatory_staleness.py` on a weekly cron (plus manual `workflow_dispatch`) — the "continuously, in production" half of the claim, since there is no always-on deployed server here to poll instead.
- `backend/app/main.py` — FastAPI app tying it together. Three `@app.middleware("http")` layers, and their order is load-bearing: Starlette makes the *last* registered the outermost, so `audit_log_middleware` wraps `limit_body_size` wraps `rate_limit` — which is what makes a 413 or a 429 an audited, measured event rather than an invisible one. Two helpers keep those layers bounded: `_is_audited(path)` restricts audit rows to `/api/*` (in the container this same app also serves the SPA's shell and assets — a row per asset per page load would be noise, and enough of it to undo the point of a bounded table), and `_route_label(...)` templates ids and numeric segments out of the metrics key (`GET /api/uploads/{id}/page/{id}`) so the collector grows with the API surface, not with traffic. The bottom of the module mounts the built SPA behind a single catch-all when `frontend/dist` exists — present in the container image, absent in dev where Vite serves it and proxies `/api` here. It is one catch-all rather than `app.mount("/", StaticFiles(...))` plus a fallback: a Mount swallows its whole prefix, so a react-router deep link would 404 on refresh, and putting the fallback route first instead shadows the real asset files. An unknown `/api/*` path still 404s as JSON.
- `Dockerfile` — one deployable image: multi-stage (Node builds the frontend, Python runtime serves both), with Tesseract and the Postgres client installed so OCR and `backup.py` work inside it. The `HEALTHCHECK` asserts `db_connected` from `/api/health` rather than merely that a response came back — `/api/health` answers `200` with `"status": "degraded"` when the process is up but Postgres is unreachable, so a liveness-only check would call that healthy. `.github/workflows/ci.yml` builds and smoke-tests the image alongside the test/lint/type-check jobs; there is no deploy step, because there is no hosted environment to push to (single-tenant, run by the issuer) — catching a broken image build is the part with real value.
- `backend/scripts/seed_demo.py` — pushes `data/demo_company/` fixtures through the real API (exercises confirmation the same way the wizard does) for fast manual testing.
- `backend/scripts/backup.py` — cron-able `pg_dump --format=custom` + a copy of the encrypted uploads vault into a timestamped directory, pruned to the last N. Also owns audit retention (`--audit-retention-days`), which deletes old `audit_events` rows **only after a successful dump** — the rows it drops are already inside that run's backup. Standalone: it shells out to `pg_dump`/`psql` and never imports the app, so it has no async/DB plumbing of its own and degrades to a warning when the client tools aren't installed.
- `DEMO_RUNBOOK.md` — demo-day script, planted-contradiction reference, and judge Q&A honesty answers.
- `frontend/src/pages/` — `Eligibility` → `Wizard` (with fact-confirmation screens) → `GapReport` → `DraftViewer` (citations clickable) and `BankerDashboard`.
  - **Mobile responsiveness + accessibility**: real SME promoters use whatever device they have — a phone between other work, not a judge's laptop — so this isn't cosmetic. Most pages already carried solid responsive Tailwind breakpoints and semantic ARIA (`GapReport.tsx`/`Eligibility.tsx` in particular: `role="radiogroup"`/`aria-checked`, `role="alert"`/`aria-live`, `aria-expanded`); the real gap was the app shell. `App.tsx`'s nav now collapses to a hamburger menu below `sm` (5 nav links + the schema chip + name/role + sign-out previously had nowhere to go on a narrow screen but overflow or wrap unreadably) — closes itself on route change via `useLocation`, and the desktop/mobile nav panels are mutually exclusive via Tailwind's `hidden`/`sm:hidden` (not just conditional React state), so there is never a moment with two `<nav aria-label="Main navigation">` landmarks simultaneously in the accessibility tree. Also added: a skip-to-main-content link (first focusable element, `sr-only` until focused); an app-wide `:focus-visible` outline in `index.css` (WCAG 2.4.7) as a safety net beyond the handful of elements with explicit `focus:ring`; a mobile-only `font-size: 16px` floor on `input`/`select`/`textarea` (below 16px, iOS Safari auto-zooms the viewport on focus — a real usability papercut for a form-heavy app, not a nitpick); `Eligibility.tsx`'s four money/number inputs previously called `focus:outline-none` without a compensating visible indicator (now paired with `focus:ring-2`), and its Yes/No disqualification toggle grows to a 44px (`2.75rem`) touch target and stacks full-width below `sm` rather than staying cramped alongside a long label. Two `text-gray-400` labels (`App.tsx`'s schema chip, `DraftViewer.tsx`'s benchmark chapter note) measured at 2.54:1 against white — under WCAG AA's 4.5:1 for normal text — and moved to `text-gray-500` (4.83:1, verified via the WCAG relative-luminance formula, not eyeballed).
  - `Wizard.tsx` save-and-resume: a demo run is one sitting (`seed_demo.py`), but a real promoter fills this across multiple sessions, and closing the tab used to mean coming back to a blank form even though every "Save answer" click already durably persisted the fact server-side (Postgres) — nothing on load ever read it back. Only *untouched* (pristine) questions are ever hydrated this way, so it can't clobber an edit already in progress this session. ## The Checklist Schema (build this first)

Machine-readable YAML, one entry per disclosure requirement:

```yaml
- id: capital_structure.share_capital_history
  clause_ref: "ICDR Sch. VI Part A (as applied by Ch. IX), para ..."
  section: "Capital Structure"
  title: "History of equity share capital"
  description: >
    Build-up of share capital since incorporation: date, number of shares,
    face value, issue price, nature of consideration, nature of allotment.
  applicability: always            # or a condition, e.g. "has_convertibles"
  required_facts:
    - share_allotments[]           # keys into the fact-store ontology
  responsible_role: promoter       # promoter | auditor | banker | system
  severity: blocker                # blocker | material | minor
  output_targets: [drhp, abridged] # which assembled documents include it
```

Rules:
- Every entry cites its clause. No orphan requirements.
- `responsible_role` drives the gap-report routing and the certification lock.
- The wizard's question flow and the generator's section plan are both *derived* from this schema — never hand-maintained in parallel.
- The schema file header pins the regulation version and amendment date it encodes.
- Initial generation of entries can be LLM-assisted from the regulation text in `data/regulation/`, but **every entry is human-reviewed before it ships** — the schema is legal-adjacent content.

## Conventions

- Python: type hints everywhere, Pydantic models for all API payloads and the schema loader, `ruff` for lint/format.
- Frontend: functional components, TypeScript, Tailwind.
- All monetary values in INR as integers (paise) or `Decimal` — never floats. Lakh/crore formatting at the display layer only.
- Dates: ISO 8601 at API boundaries, timezone-aware internally (IST context).
- Facts are immutable once confirmed; corrections create a new fact version with provenance to the old one.
- LLM access behind a single provider-agnostic client (free tiers: Gemini / Groq); temperature 0 for generation and validation; every LLM call logs its prompt-context fact IDs so citations are reconstructible.
- The demo company is clearly synthetic (fake CIN/PAN-format identifiers, a name like "Sunrise Agrotech Ltd") — never real business data.

## Known Limitations (state them if asked — never hide them)

- **Security hardening is real but scoped.** Request bodies are size-bounded (`Settings.max_request_body_bytes`, default 20 MB) via a global Content-Length check plus a bounded read loop on the upload endpoint specifically; uploaded filenames are sanitised (basename-only, control-character-stripped, length-capped) before they flow into provenance/exported documents; numeric/string inputs (eligibility figures, litigation query, fact keys/snippets, auth email/name/password) carry sanity bounds; the Gemini API key travels as a header (`x-goog-api-key`), never a URL query param, so it can't leak into request-URL logging. Rate limiting is now real but in-process (`app.rate_limit`): the window state is per-process memory, so N worker processes mean N independent budgets, and a restart clears them — correct for the single-instance deployment this targets, not for a horizontally-scaled one (that needs Redis or equivalent shared state). CORS origins come from `Settings.allowed_origins` rather than a hardcoded dev value. Still not built: virus/malware scanning of uploads, a WAF — appropriate for a single-tenant deployment behind normal network controls, not a hardened multi-tenant public endpoint.
- **Audit log is in Postgres now, but retention is opt-in and there is still no UI.** `app.audit` writes to the append-only `audit_events` table, which removed the old flat file's O(n)-per-request rewrite. Retention is enforced by `backend/scripts/backup.py --audit-retention-days N`, which deletes rows older than N days **only after a successful `pg_dump`** — so the rows being dropped are already inside that run's backup; the default is 0 (keep everything). `GET /api/audit` is banker-only with no pagination beyond a `limit` cap (default 200, max 2000), and there is still no frontend for it, only the API.
- **Encryption at rest, where it still applies, is single-key with no rotation.** Facts, review state, and user accounts now live in Postgres (see `backend/app/db.py`) — encryption at rest for that data is a database/infrastructure concern (e.g. RDS/Cloud SQL disk encryption), not application code, and isn't configured in this dev-grade `docker-compose.yml`. Archived original uploads are still application-level encrypted (`app.crypto`, Fernet/AES-128-CBC+HMAC); the audit log is not — it moved into Postgres and inherits whatever the database is configured with — one active `ENCRYPTION_KEY` with no rotation/versioning scheme and no KMS integration. Losing the key means losing everything it encrypted (by design — there's no backdoor); rotating it today means re-encrypting everything by hand. Leaving it unset is a valid *local dev* choice (falls back to a per-process random key, logged as a warning) but not a valid *production* one.
- **Postgres is single-instance, with scripted backups but no replication.** `backend/scripts/backup.py` takes a timestamped `pg_dump --format=custom` plus a copy of the encrypted uploads vault, prunes to the last N backups, and is designed to be cron'd — a real, restorable backup, and it degrades to a warning rather than a crash when `pg_dump` isn't installed. What it is *not* is continuous durability: WAL archiving, point-in-time restore, and replicas are production infrastructure, not configured here, and nothing verifies a restore actually works. There is also no multi-tenancy: one deployment still serves one issuer's promoter/auditor/banker team (no `tenant_id`/`company_id` anywhere in the schema) — see the architecture note at the top of `backend/app/main.py`.
- **Auth has no account-admin UI.** Auditor/banker registration is gated by a shared invite code (`Settings.auditor_invite_code` / `banker_invite_code`), not per-user invites from an admin console — appropriate for one issuer's small promoter/auditor/banker team, not a multi-firm SaaS. There's no password reset flow either. `JWT_SECRET_KEY` must be set in production `.env`; unset, the app falls back to a per-process random key (documented, logged as a warning) and every restart invalidates all sessions.
- **Restated financial statements are auditor work by law.** The tool ingests and formats them; it cannot and does not generate them. The coverage score marks them out-of-scope explicitly.
- **The litigation lookup is real but structurally limited.** `IndianKanoonConnector` genuinely calls api.indiankanoon.org (verified against the API's own reference client, and against the live server itself — an invalid-token request correctly gets a real `401 Invalid token.` back, not a connection failure). But IndianKanoon indexes *published judgments* — Supreme Court, High Court, tribunal decisions already handed down. It has no concept of a currently pending trial-court case, and **no free public API exists for that** — India's live case-status registry (eCourts/NJDG) has none. A clean result from this connector means "no published judgment names this entity," not "no litigation exists." Requires `LITIGATION_PROVIDER=indiankanoon` + a paid `INDIANKANOON_API_TOKEN` (new accounts get ₹500 free trial credit at api.indiankanoon.org/signup/); unset, the app runs on the offline mock with zero behavior change to callers.
- **The checklist schema is human-reviewed but not legally certified.** It's a faithful encoding of the regulation, not legal advice.
- **Extraction can misread documents — more so for OCR'd ones.** Mitigated (not eliminated) by mandatory promoter confirmation against the highlighted source, clickable citations for the banker's review, and a lower confidence score for anything read via OCR rather than a native text layer (`_OCR_CONFIDENCE = 0.6`, under the examiner's existing 0.7 low-confidence threshold, so every OCR-sourced fact is automatically flagged for extra scrutiny). OCR itself (`app.intake.ocr`) requires a real Tesseract install as a **system binary** on the machine running the backend — it does not ship with this repo (pip installs the Python wrapper, not the OCR engine). Without it, scanned pages and photographed uploads simply extract nothing (never a crash) — same as an empty page today.
- **Regulation version is pinned as of build date** (ICDR as amended through 2026-03-21; see `data/regulation/MANIFEST.md`). Any later amendment requires regenerating the schema — `app.regulatory_watch`'s staleness watcher flags when SEBI has published anything ICDR-tagged more recently than the pin (weekly via `.github/workflows/regulatory-staleness.yml`, or on demand from the Banker Dashboard), but it scrapes SEBI's public site rather than a documented API, is scoped to items surfaced by an "ICDR" keyword search (not exhaustively verified complete against every SEBI publication channel), and — like the litigation connector — surfacing a candidate item is not the same as confirming it's a notified amendment requiring a schema change; that judgment still needs a human.
- **The output is a draft, not a filing.** It becomes submittable only after merchant banker due diligence and certification — this is by design and matches the problem statement.
- **Vernacular draft review has no offline path.** Unlike every other LLM-dependent feature in this app, `app.generate.translate` has no deterministic fallback — there is no non-LLM way to translate prose. Without a configured key (or if the call fails, or the result fails the number-preservation guard), `GET /api/sections/{entry_id}/translate` still answers `200` with `translated: false` and the untouched English original — never an error — but the promoter genuinely sees English until a key is configured. The filed DRHP itself is never translated; this is a review aid only.

## What NOT to Do

- **Never let the LLM invent facts, numbers, names, or clause citations.** If it's not in the fact store, it's `[REQUIRES INPUT]`.
- **Never position the tool as replacing merchant bankers** or as producing a filing-ready document without certification — that contradicts the problem statement and SEBI's regulatory intent.
- Don't put real company data, real financials, or real personal identifiers in the repo — synthetic demo issuer only. Reference DRHPs in `data/reference_drhps/` are public filings used for benchmarking, not templates to copy text from (the boilerplate detector exists for a reason).
- Don't hardcode disclosure requirements in prompts or code — everything flows from the schema.
- Don't expand scope to main-board IPOs, rights issues, or non-Chapter-IX frameworks.
- Auth/RBAC is now real (see `backend/app/auth/`) — JWT bearer tokens, hashed passwords, server-enforced role checks. Don't build e-sign plumbing or multi-tenant account admin beyond what's there — mention it in docs instead.
- Don't chase generation eloquence at the cost of traceability — a plainly worded, fully cited section beats beautiful uncited prose.
